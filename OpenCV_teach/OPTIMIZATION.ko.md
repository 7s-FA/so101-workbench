# 원본 성능 개선 기록

이 문서는 원본 배포 당시 기록입니다. 아래 영문 버튼 이름과 성능 측정은 당시 기준이며,
현재 실행 방법과 한국어 UI는 [사용방법.md](사용방법.md)를 따릅니다.

## 스페이스바로 연속 티칭

1. 기존처럼 `Connect & sync`를 누르고 동기화가 끝나면 `Start teaching`을 누릅니다.
2. 리더를 움직이다 원하는 위치에서 **스페이스바를 한 번** 누릅니다.
3. 다음 제어 사이클에서 읽은 **팔로워 실제 자세**를 `step1`, `step2` 순서로 저장합니다.
4. 추종은 계속됩니다. 바로 다음 자세를 만들고 다시 스페이스바를 누릅니다.
5. 마지막에 `Finish & Save`로 제목을 지정합니다.

각 스텝은 기존 `poses_*.json` 자동 저장에도 반영됩니다. 스페이스바를 누르고 있는 동안
중복 스텝을 만들지 않습니다. 입력창·이름 수정·모달 확인창 및 TEACH 이외 상태에서는
이 단축키로 스텝을 기록하지 않습니다. 기존 HOLD 상태의 `Add step` 안정성 검사는 유지합니다.
스페이스바 저장은 움직이는 중에도 가능하므로 리더 목표와 실제 팔로워 자세가 다를 수 있습니다.
연속 궤적 녹화가 아닌 관절 자세 스텝 기록입니다.

## 설정은 settings.toml 한 곳에서

프로그램 폴더의 `settings.toml`을 텍스트 편집기로 수정하고 재시작합니다.
각 항목에 한국어 설명, 단위, 허용 범위를 달았습니다. 별도 설정 패키지는 필요 없습니다.

| 구역 | 설정 내용 |
|---|---|
| response | 제어 주기, 화면 갱신, 건강 검사 주기, 응답 감시 |
| motion | 몸체·그리퍼·동기화 속도, 단계 대기 시간, 이동 제한 |
| safety | 온도, 정체 감지, 활성화와 초기 자세 허용량 |
| capture | 단계 기록 안정성, 단계 수, 이름 길이 |
| logging | CSV·온도·재생 로그, 정지 후 진단 |
| dashboard | 진단 창 갱신·표본 보관·오래된 데이터 표시 |
| diagnostic_cli | 별도 어깨/온도 진단 도구의 기본값 |
| arrival_tolerances | 각 관절 도착 허용 오차 |
| paths / appearance | 로그 폴더, 창 크기 |

주로 `CONTROL_HZ`, `GUI_POLL_MS`, `COMMAND_RATE`, `GRIPPER_COMMAND_RATE`,
`ARRIVAL_SETTLE_SECONDS`를 확인하면 됩니다. `COMMAND_RATE`는 모터 실제 속도 보장이 아니라
목표 변화율입니다. 이번 변경에서는 몸체 30도/초, 그리퍼 40포인트/초, 초기 동기화 5단위/초를
유지했습니다. 보호/속도 항목은 기존 검증 상한 안에서만 조절하도록 범위를 검사합니다.
잘못된 이름, 누락, 자료형, 범위, 서로 모순되는 설정은 시작 시 오류로 안내합니다.
CLI 인자가 제공되면 그 실행의 해당 기본값을 덮어씁니다.

`robot.json`의 USB·로봇 쌍 식별과 `calibration/`의 보정값은 등록/보정 도구가 생성하는
하드웨어 고유 데이터이므로 분리 유지합니다. 장치 레지스터 주소, 패킷 구조, 서보 PID와
전류·토크 보호값은 임의 사용자 튜닝 항목으로 노출하지 않았습니다.

## 반응속도 변경

- 제어 목표 30 → 100Hz, GUI 확인 간격 50 → 16ms.
- 명령 입력 시 제어 루프 대기를 즉시 깨웁니다. STOP도 즉시 깨웁니다.
- 연속 위치 표시 이벤트는 최신 것만 남겨 오래된 화면 갱신이 밀리지 않게 합니다.
- 일반 건강 검사: 모터당 개별 읽기 3회 → 검증된 블록+단일 온도 읽기 2회.
  전체 18 → 12 패킷이며 상태/토크/온도 검사를 유지합니다. 온도는 두 방식 모두 검사합니다.
- 진단 창을 함께 쓰면 같은 사이클에서 이미 읽고 검증한 값을 건강 검사에 재사용합니다.
- CSV 일반 flush를 1초 간격으로 묶었습니다. 정체 오류/정상 종료 시 남은 버퍼도 반영합니다.
  강제 종료나 전원 차단 시 최근 약 1초의 CSV 버퍼는 남지 않을 수 있습니다.
  스텝 JSON 원자적 저장은 기존처럼 즉시 수행합니다.
- 스텝 추가 때 전체 목록을 재생성하지 않고 새 행만 추가합니다.
- 세션 보고서에 실제 루프 평균 Hz, 최대 간격, 목표 초과 사이클 수와 적용 설정을 남깁니다.

건강 검사는 기존 0.5초(그리퍼 진단 0.2초) 주기를 유지합니다. 모터 통신은 한 worker에서
순서대로 처리하며, 이미 진행 중인 시리얼 읽기의 타임아웃을 강제로 중단하지는 않습니다.
USB 읽기·건강 검사·선택적 상세 진단이 오래 걸리면 목표 100Hz보다 낮아질 수 있습니다.

## 현재 Ubuntu 환경에서 실행·검사

현재 작업 폴더는 `/path/to/Final_Arm/OpenCV_teach`, Python은 `/path/to/venv/bin/python`입니다. ZIP을 새로 풀거나 별도 `.venv`를 만들 필요가 없습니다. 기본 프로필은 리더가 필요 없는 `follower.json`이며, 실제 사용 순서는 [사용방법](사용방법.md)을 따릅니다.

```bash
cd /path/to/Final_Arm
bash OpenCV_teach/run.sh --demo
bash OpenCV_teach/run_tests.sh test_optimization
bash OpenCV_teach/run.sh --check-only
bash OpenCV_teach/run.sh
```

기본 명령 `bash OpenCV_teach/run_tests.sh`는 핵심 21개 검사를 실행합니다. 다른 변경은 필요한 모듈·케이스를 인수로 지정합니다. 이 실행기를 사용하면 이번 검사에서 새로 생성된 지정 MuJoCo 로그만 정리합니다. 이전 검증 기록에는 도킹 기준·실물 조정·온도 지속 판정·상태 모니터링을 포함한 138개 회귀 검사 통과가 있습니다. 현재 정리 작업의 결과는 `verification/20260922_workflow_cleanup/validation.txt`를 따릅니다. 아래 Windows 결과는 원본 개발 당시 이력입니다.

## 확인한 범위

Windows의 번들 Python에서 추가 회귀 테스트 13개 통과.
설정 오류 거부, 이벤트 순서, 속도/정체 제한, 연속 스텝 기록·파일 저장·재생,
GUI 응답 감시 정지, 12패킷 건강 검사, 온도·알람·체크섬·토크 오류,
진단값 재사용, X11 형식의 반복 입력/입력창 제외를 검사했습니다.
Linux OS 전용 helper만 Windows 테스트에서 대체했으며 실제 모터에 연결하지 않았습니다.
Tk GUI 위젯 생성, 연속 스페이스바 handler, 자동 JSON 저장, TEACH 유지, 종료를 확인했습니다.
물리 키보드의 Ubuntu/X11/Wayland 이벤트와 실제 모터 동작은 여기서 검증하지 못했습니다.

원본 Windows 환경에서 각 2초의 DEMO 제어 루프 측정: 기존 약 21.4Hz, 수정 약 64.0Hz.
Windows 타이머 영향을 포함하는 참고 측정이며 Ubuntu/실제 USB 통신 성능 보장이 아닙니다.
원본 README의 테스트 92개는 원본 제작 당시 기록이고, 이번 테스트 결과와 별개입니다.
